# 第3章-5 ドメインモデリングの進め方

ここまでの章では、Entity や Value Object などの「モデルの部品」を見てきました。しかし実務で難しいのは、部品の書き方よりも「どんなモデルを作るべきか」を見つけることです。この章では、モデルを見つける過程を扱います。

## モデルは会話から見つかる

DDDでは、モデルは開発者が机上で考えるものではなく、ドメインエキスパートとの会話を通じて見つけるものです。

ドメインエキスパートとは、その業務に詳しい人です。専任の担当者がいるとは限らず、プロダクトオーナー、営業担当、カスタマーサポート、あるいはユーザー自身がその役割を担うこともあります。

会話で注目すべきなのは、次のような言葉です。

- 名詞: 概念の候補(タスク、期限、担当者)
- 動詞: 振る舞いの候補(完了する、アーカイブする、割り当てる)
- 「〜のときは〜できない」: 不変条件の候補(完了済みのタスクは名前を変えられない)
- 「〜したら〜する」: イベントや副作用の候補(完了したら通知する)
- 「場合による」: 隠れた概念やルールの候補

特に「場合による」という答えは重要です。その「場合」が何で決まるのかを掘り下げると、まだモデルに現れていない概念が見つかることがよくあります。

## Event Storming

Event Storming は、業務の流れを「起きた出来事」の時系列で洗い出すワークショップ手法です。付箋とホワイトボードがあれば始められ、開発者とドメインエキスパートが同じ場で議論できるのが特徴です。

基本的な進め方は次の通りです。

1. **ドメインイベントを並べる**: 「タスクが作成された」「タスクが完了した」のように、過去形で業務上の出来事を書き出し、時系列に並べる
2. **コマンドを置く**: 各イベントを引き起こした操作(「タスクを完了する」)をイベントの前に置く
3. **アクターを置く**: そのコマンドを誰が実行するか(ユーザー、システム、外部サービス)を書く
4. **ポリシーを見つける**: 「イベントが起きたら次のコマンドを実行する」という自動的な反応(「完了したら通知する」)を書く
5. **Aggregateを見つける**: コマンドを受け付け、ルールを判断してイベントを出す主体をまとめる
6. **境界を引く**: 言葉の意味が変わる場所に線を引き、Bounded Context の候補にする

### タスク管理アプリで試すと

本書のタスク管理アプリで Event Storming をすると、次のような並びが得られます。

```text
[ユーザー] → (タスクを作成する) → 〈タスクが作成された〉
[ユーザー] → (タスク名を変更する) → 〈タスク名が変更された〉
[ユーザー] → (タスクを完了する) → 〈タスクが完了した〉 → ポリシー: 完了したら通知する
[ユーザー] → (タスクをアーカイブする) → 〈タスクがアーカイブされた〉
```

この結果は、そのまま本書のコードに対応しています。

| Event Storming の要素 | コード上の表現 |
|---|---|
| コマンド | `TaskApplicationService::complete_task` |
| Aggregate | `Task` |
| ドメインイベント | `TaskEvent::TaskCompleted` |
| ポリシー | `TaskCompletionNotifier` を呼ぶ処理 |
| ルール | `Task::complete` が返す `TaskError` |

さらに、議論の中で「完了済みのタスクの名前は変えられるのか」という問いが出れば、それが `TaskError::TaskNotOpen` という不変条件になります。

## 具体例でモデルを検証する

抽象的な議論だけでは、モデルの穴に気づけません。具体的なシナリオを使って、モデルが業務を正しく説明できるか確かめます。

- 「タスクを完了したあとで誤りに気づいたら、どうしますか」
- 「アーカイブしたタスクを元に戻したいことはありますか」
- 「同じ名前のタスクを2つ作ってもよいですか」

こうした問いへの答えが、モデルの修正点になります。Rustでは、このシナリオをそのままテストとして書けます。

```rust
#[test]
fn archived_task_cannot_be_renamed() {
    let mut task = Task::new(
        TaskId::new("task-1").unwrap(),
        TaskTitle::new("牛乳を買う").unwrap(),
    );
    task.archive().unwrap();

    let result = task.rename(TaskTitle::new("卵を買う").unwrap());

    assert!(result.is_err());
}
```

テスト名が業務の言葉で書かれていれば、ドメインエキスパートにもテストの意図を説明できます。

## モデルは繰り返し作り直す

最初のモデルが正しいことはまずありません。DDDでは、実装を通じて業務理解が深まり、それに合わせてモデルを作り直す過程を前提にしています。

モデルを見直すきっかけには、次のようなものがあります。

- 新しい要件を既存のモデルで表現すると、不自然な分岐が増える
- ドメインエキスパートが、コードの名前とは違う言葉で説明する
- テストを書こうとすると、準備が異様に複雑になる

Rustは型システムが強いため、モデルを変えたときに影響範囲をコンパイラが教えてくれます。これは作り直しの心理的なコストを下げる大きな利点です。

## よくある誤解

- モデリングは設計フェーズで完了させ、実装中は変えないものだと思いがち
- データベースのテーブル設計から始めればモデルになると考えがち
- ドメインエキスパートの言うことをそのまま実装すればよいと思いがち

テーブル設計から始めると、データの構造は見えても振る舞いやルールが見えにくくなります。また、ドメインエキスパートの説明には曖昧さや矛盾が含まれることがあります。それを問い直し、一緒にモデルを磨いていくのが開発者の役割です。
