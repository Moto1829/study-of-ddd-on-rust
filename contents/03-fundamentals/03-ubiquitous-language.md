# 第3章-3 ユビキタス言語をコードに反映する

ユビキタス言語(Ubiquitous Language)は、開発者とドメインエキスパートが同じ意味で使う共通の言葉です。DDDの戦術的パターンはどれも、この言葉をコードへ正確に写すための手段だと捉えると理解しやすくなります。

用語集を作ること自体が目的ではありません。重要なのは、会話・ドキュメント・コード・テストで同じ言葉が同じ意味を持ち続けることです。

## なぜ言葉を揃えるのか

言葉がずれると、翻訳コストが発生します。

- 業務担当者は「タスクを片付ける」と言う
- 仕様書には「タスクをクローズする」と書かれている
- コードでは `task.set_status(2)` になっている

この状態では、「片付ける」と「クローズ」と `status = 2` が同じ意味なのか、毎回誰かが確認しなければなりません。しかも確認のたびに解釈が少しずつずれ、やがてバグになります。

ユビキタス言語は、この翻訳を不要にするための約束です。

## コードのどこに言葉が現れるか

Rustでは、ユビキタス言語は次の場所にそのまま現れます。

| 言葉の種類 | Rustでの表現 | タスク管理アプリの例 |
|---|---|---|
| 概念 | struct / enum の型名 | `Task`, `TaskTitle`, `TaskStatus` |
| 状態 | enum のバリアント | `Open`, `Completed`, `Archived` |
| 業務上の操作 | メソッド名 | `complete`, `archive`, `rename` |
| 起きた事実 | イベント型 | `TaskEvent::TaskCompleted` |
| ルール違反 | エラーのバリアント | `TaskError::TaskAlreadyCompleted` |
| ユースケース | Application Service のメソッド | `complete_task`, `archive_task` |

特に見落とされやすいのが、エラーとイベントです。`TaskError::TaskNotOpen` は「Open状態でないタスクには許されない操作がある」という業務ルールを、名前で説明しています。これを `InvalidOperation` のような汎用名にすると、ルールの存在がコードから読み取れなくなります。

## setter はユビキタス言語を消す

次の2つを比べてみます。

```rust
// 業務上の言葉が消えている
task.set_status(TaskStatus::Completed);

// 業務上の言葉がそのまま残っている
task.complete()?;
```

前者は「状態を Completed に書き換える」という技術的な操作しか表していません。後者は「タスクを完了する」という業務上の行為を表し、さらに `Result` によって「完了できない場合がある」ことまで伝えています。

ドメインエキスパートに `set_status` を見せても意味は伝わりませんが、`complete` なら会話の言葉と一致します。Entityにsetterではなく振る舞いを持たせる理由の1つはここにあります。

## 言葉のずれを見つける兆候

次のような状態は、ユビキタス言語が崩れ始めているサインです。

- コードレビューで「この `flag` は何の意味?」という質問が繰り返される
- 業務担当者との会話で、コード上の名前を毎回言い換えている
- 同じ概念に `item`、`todo`、`task` など複数の名前が混在している
- `Manager`、`Helper`、`Util`、`Data` のような意味を持たない名前が増えている
- 仕様変更の議論で、どのコードを直せばよいかすぐに特定できない

こうした兆候が出たら、まず名前を直す価値があります。Rustでは型名やメソッド名の変更をコンパイラが追跡してくれるため、リネームのコストは比較的低く済みます。

## 言葉が変わったらコードも変える

ユビキタス言語は固定されたものではなく、業務理解が深まるにつれて変わります。

たとえば最初は「アーカイブ」と呼んでいた操作が、業務担当者との会話を重ねるうちに「保管」と呼ばれるようになったとします。このとき、会話では「保管」、コードでは `archive` のまま放置すると、また翻訳が必要になります。

言葉の変化はモデルの変化です。会話の言葉が変わったら、型名・メソッド名・テスト名も一緒に変えることを習慣にすると、モデルとコードのずれが蓄積しにくくなります。

## 英語と日本語の扱い

日本語で議論しているチームでは、コード上の英語名との対応が問題になりがちです。現実的な方法は、用語集で日本語と英語の対応を1対1に固定することです。

| 日本語 | コード上の名前 | 意味 |
|---|---|---|
| タスク | `Task` | 個人が管理する作業単位 |
| タスク名 | `TaskTitle` | 1〜100文字のタスクの名前 |
| 完了する | `complete` | Open状態のタスクをCompletedにする |
| アーカイブする | `archive` | タスクを一覧から外し、以後の変更を禁止する |

この表の価値は、翻訳の揺れをなくすことにあります。同じ日本語に対して `finish` と `complete` が混在し始めたら、どちらかに統一します。

## よくある誤解

- ユビキタス言語は最初に用語集を作れば終わりだと思いがち
- 業務担当者の言葉をそのまま使えば、それがユビキタス言語になると考えがち
- 技術用語(`Repository` や `Dto`)もユビキタス言語に含めるべきだと思いがち

ユビキタス言語は、業務の会話を通じて磨かれていく言葉です。業務担当者の言葉が曖昧なら、開発者が問い直して意味を確定させる過程も含まれます。また、`Repository` のような技術用語は開発者同士の言葉であり、ドメインの言葉と混ぜない方が境界が明確になります。
