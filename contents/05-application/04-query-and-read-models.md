# 第5章-4 一覧取得と検索をどう設計するか

登録や更新のユースケースはDDDの入門で扱われやすい一方、一覧取得や検索は後回しにされがちです。しかし実務では、むしろ一覧画面や検索APIの方が頻繁に必要になります。

この章は、一覧取得と検索を概念レベルで整理する章です。後続の第6章では、ここで述べた考え方を具体的な型と実装へ対応付けます。

## 一覧取得は常にAggregateを返すべきか

結論から言うと、常にそうとは限りません。書き込みのために厳密な整合性を持つAggregateと、画面表示のための一覧データは要求が違うからです。

この違いが重要になるのは、一覧画面で必要な情報と更新時に必要な情報が本質的に異なるからです。たとえば100件のタスク一覧を表示したい場面では、各 `Task` の整合性を保つための完全な状態よりも、ID・タイトル・状態のような表示に必要な要約情報だけが取れれば足ります。一方で個別更新では、状態遷移や不変条件を正しく扱うために、Aggregateとしての完全な状態が必要です。

たとえば、タスク一覧画面では次の情報だけ欲しいことがあります。

- ID
- タイトル
- 状態
- 期限や担当者の要約

さらに実務では、一覧表示のために次のような情報が欲しくなることがあります。

- 並び順のための更新日時
- バッジ表示のための件数情報
- 別テーブル由来の担当者名
- 検索ヒット箇所の強調表示に使う補助情報

このとき、毎回完全なAggregateを読み出すより、一覧表示専用の読み取りモデルを返した方が責務が明確になります。

特に、一覧で100件単位のデータを返すのに各件を完全なAggregateとして組み立て始めると、設計上も性能上も無理が出やすくなります。更新時に必要な厳密さを、表示時にも同じ形で要求する必要はありません。

## タスク管理アプリでの分け方

この本のタスク管理アプリでは、書き込み側の `TaskRepository` とは別に、読み取り側として `TaskSummaryReader` を追加しています。これはCQRSを全面採用するというより、「一覧取得は別モデルで扱ってよい」という実務的な整理です。

```rust
pub struct FindTasksQuery {
    pub status: Option<TaskStatusDto>,
    pub page: u64,
    pub per_page: u64,
}

pub struct TaskSummary {
    pub id: String,
    pub title: String,
    pub status: TaskStatusDto,
}
```

読み取り専用のインターフェースは、たとえば次のように置けます。

```rust
pub trait TaskSummaryReader {
    fn find(&self, query: FindTasksQuery) -> Result<Vec<TaskSummary>, QueryError>;
}
```

このようにしておくと、書き込み用の `TaskRepository` はAggregateの保存と再構築に集中し、一覧取得の都合は `TaskSummaryReader` 側へ閉じ込められます。

ここで重要なのは、`TaskSummary` がドメインモデルそのものではないことです。これは表示や一覧取得のための読み取り専用データです。

言い換えると、この章で押さえたいのは「更新モデルと読み取りモデルは同じでなくてよい」という原則です。実際にどの型をどこへ置くかは、第6章で改めて確認します。

## Query と Repository を分ける判断基準

この分離を大げさに感じるときは、次の観点で考えると整理しやすくなります。

- 更新で不変条件を守る必要があるか
- 一覧表示のためだけの項目を含むか
- 集計やJOINの都合が強いか
- ページングやソートが中心の関心事か

これらが強いなら、RepositoryよりQuery側に寄せた方が自然です。逆に、単一のAggregateを読み出してすぐ更新するような処理なら、Repositoryで十分です。

重要なのは、Repositoryが古い、Queryが新しい、という話ではありません。それぞれが扱う責務が違うだけです。

## 検索条件をどこへ置くか

一覧取得や検索では、次のような条件がよく出ます。

- ステータスで絞り込む
- ページングする
- 並び替える
- フリーワード検索する

こうした条件は、書き込み用Repositoryへ無理に押し込むより、Query用のモデルとして明示した方が読みやすくなります。書き込みと読み取りの関心事を混ぜすぎないことが大切です。

たとえば、次のように並び順まで型として明示しておくと、呼び出し側の意図がはっきりします。

```rust
pub enum TaskSort {
    CreatedAtDesc,
    DeadlineAsc,
}

pub struct FindTasksQuery {
    pub status: Option<TaskStatusDto>,
    pub keyword: Option<String>,
    pub page: u64,
    pub per_page: u64,
    pub sort: TaskSort,
}
```

この設計の利点は、引数の数を減らすことではありません。検索というユースケースがどんな入力を受け取るのかを、型の形で読めることにあります。

## どこまでをドメイン層へ持ち込むか

一覧取得や検索を考え始めると、すべてをドメインモデル中心で解きたくなることがあります。しかし、読み取りモデルは「ドメインルールを守るためのモデル」ではなく、「必要な情報を返すためのモデル」です。

この違いを意識しておくと、次のような整理がしやすくなります。

- `Task` は状態遷移や不変条件を守る
- `TaskSummary` は表示に必要な情報を返す
- `FindTasksQuery` は検索条件を表現する

この3つの責務を混ぜないだけでも、コードの読みやすさはかなり上がります。

## 失敗しやすい設計

よくある失敗は、一覧取得の要求をすべて `TaskRepository` に足し続けることです。最初は `find_all` だけでも、そのうち `find_by_status`, `find_by_status_and_keyword`, `find_recent_open_tasks_ordered_by_deadline` のようにメソッドが増えていきます。

これはRepositoryが悪いのではなく、更新責務と検索責務を同じ入口へ集めすぎているのが問題です。

もう1つの失敗は、画面表示専用の文字列整形までQueryサービスに埋め込みすぎることです。検索条件や取得形はQuery側の責務ですが、最終的な表示文言まで抱え込むと、今度はプレゼンテーション都合が混ざり始めます。

## よくある誤解

- 一覧取得でも必ずAggregateを返すべきだと思いがち
- Queryを分けると大げさなCQRSになると感じやすい
- 一覧画面用DTOを作るのは冗長に見えやすい

実際には、更新責務と表示責務は別物です。特に実務では一覧の要求が肥大化しやすいため、早い段階で読み取りモデルを分ける発想を知っておくと設計しやすくなります。

この章の段階では、「別モデルを許容する」理解で十分です。イベントストアや非同期投影まで進めなくても、読み取り専用の型を切り出すだけで設計上の圧力はかなり減らせます。
