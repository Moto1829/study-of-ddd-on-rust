# 第7章-17 レイヤードとヘキサゴナル・オニオン・クリーンアーキテクチャ

DDDを学んでいると、ヘキサゴナルアーキテクチャ、オニオンアーキテクチャ、クリーンアーキテクチャといった名前をよく目にします。本書のサンプルは `domain` / `application` / `infrastructure` の3層で構成していますが、これらのアーキテクチャとどういう関係にあるのでしょうか。この章では、それぞれの考え方を比較し、本書の構成がどこに位置するかを整理します。

## 伝統的なレイヤードアーキテクチャ

最初に、エリック・エヴァンスのDDD本で示された、伝統的なレイヤードアーキテクチャを見ます。

```text
┌────────────────────┐
│  プレゼンテーション層 │
├────────────────────┤
│  アプリケーション層   │
├────────────────────┤
│  ドメイン層         │
├────────────────────┤
│  インフラストラクチャ層 │
└────────────────────┘
       依存の方向: 上から下へ
```

この構成では、上の層が下の層に依存します。ドメイン層はインフラ層に依存するため、ドメインのコードからDBアクセスのクラスを直接呼べます。

問題は、**ドメイン層がインフラ層に依存してしまう**ことです。DBのライブラリを変えると、ドメイン層まで影響が及びます。ドメインのテストにもDBが必要になります。

## 依存関係逆転の原則

この問題を解決するのが、**依存関係逆転の原則(Dependency Inversion Principle)** です。

- ドメイン層が、必要なインターフェース(Rustではトレイト)を定義する
- インフラ層が、そのトレイトを実装する

```rust
// domain 層がトレイトを定義する
pub trait TaskRepository {
    fn save(&mut self, task: Task);
    fn find_by_id(&self, task_id: &TaskId) -> Option<Task>;
}

// infrastructure 層が実装する(domain 層に依存する)
impl TaskRepository for InMemoryTaskRepository {
    // ...
}
```

こうすると、依存の方向が逆転し、インフラ層がドメイン層に依存するようになります。本書のサンプルはこの形を採っています。

以降で紹介する3つのアーキテクチャは、どれもこの原則を中心に据えたものです。

## ヘキサゴナルアーキテクチャ(Ports and Adapters)

ヘキサゴナルアーキテクチャは、アプリケーションの中心と外部の世界を、**ポート**と**アダプター**で分ける考え方です。

```text
           [Web API]     [CLI]
               ↓           ↓
          ┌─── Adapter ─ Adapter ───┐
          │      Port      Port      │
          │                          │
          │    アプリケーションの中心   │
          │   (ドメイン + ユースケース)  │
          │                          │
          │      Port      Port      │
          └─── Adapter ─ Adapter ───┘
               ↓           ↓
            [DB]      [通知サービス]
```

- **ポート(Port)**: アプリケーションの中心が定義する、外部とのやり取りの窓口。Rustではトレイト
- **アダプター(Adapter)**: ポートと外部の技術をつなぐ実装

ポートには2種類あります。

| 種類 | 方向 | 例 | 本書での対応 |
|---|---|---|---|
| 駆動する側(Driving / Primary) | 外部 → 中心 | Web API、CLI がユースケースを呼ぶ | `TaskApplicationService` の公開メソッド |
| 駆動される側(Driven / Secondary) | 中心 → 外部 | DB への保存、通知の送信 | `TaskRepository`、`TaskCompletionNotifier` |

六角形という形に意味はありません。外部とのつながりが複数あることを、図として表しやすかったというだけです。

## オニオンアーキテクチャ

オニオンアーキテクチャは、アプリケーションを同心円の層で表します。

```text
┌──────────────────────────────────┐
│  インフラストラクチャ / UI / テスト  │
│  ┌────────────────────────────┐  │
│  │  アプリケーションサービス      │  │
│  │  ┌──────────────────────┐  │  │
│  │  │  ドメインサービス       │  │  │
│  │  │  ┌────────────────┐  │  │  │
│  │  │  │ ドメインモデル   │  │  │  │
│  │  │  └────────────────┘  │  │  │
│  │  └──────────────────────┘  │  │
│  └────────────────────────────┘  │
└──────────────────────────────────┘
        依存の方向: 外から内へ
```

ルールは1つだけです。**依存は外側から内側へ向かう**。内側の層は、外側の層について何も知りません。

ドメインモデルを中心に置くという点で、DDDの考え方がそのまま図になっています。

## クリーンアーキテクチャ

クリーンアーキテクチャも、同心円で表される構成です。

| クリーンアーキテクチャの層 | 本書での対応 |
|---|---|
| Entities(エンタープライズのビジネスルール) | `domain` |
| Use Cases(アプリケーションのビジネスルール) | `application` |
| Interface Adapters(コントローラー、プレゼンター、ゲートウェイ) | `infrastructure`、`presentation` |
| Frameworks & Drivers(Web、DB、外部インターフェース) | 外部クレート、DB、HTTPサーバー |

依存のルールはオニオンアーキテクチャと同じで、外側から内側への一方向です。

クリーンアーキテクチャでは、ユースケースごとに入力と出力の型(Input Port、Output Port)を定義することを推奨しています。本書の `TaskOutput` は、Output にあたるDTOです。

## 3つの共通点

名前や図は違いますが、3つのアーキテクチャの本質は同じです。

1. **ドメインを中心に置く**: ビジネスルールが、技術の詳細から独立している
2. **依存は内側へ向かう**: 外側の技術が内側のドメインに依存し、逆はない
3. **外部とはインターフェースで接続する**: DBやUIは、トレイトの実装として差し替えられる

本書のサンプルは、3層という見た目こそ伝統的なレイヤードアーキテクチャに似ていますが、依存の方向は `infrastructure → application → domain` であり、実質的にはこれらのアーキテクチャと同じ考え方に立っています。

## Rustでの表現

Rustでは、依存の方向をモジュールの `use` で確かめられます。

```text
src/
├── domain/          # 他のモジュールを use しない
├── application/     # domain だけを use する
└── infrastructure/  # domain と application を use する
```

`domain` の中に `use crate::infrastructure` が現れたら、依存の方向が逆転しているサインです。

規模が大きくなったら、Cargo workspace でクレートを分けると、依存の方向をビルド構成で強制できます。

```toml
# crates/domain/Cargo.toml
[dependencies]
# 外部への依存なし

# crates/application/Cargo.toml
[dependencies]
domain = { path = "../domain" }

# crates/infrastructure/Cargo.toml
[dependencies]
domain = { path = "../domain" }
application = { path = "../application" }
sqlx = "0.8"
```

`domain` クレートの `Cargo.toml` に `infrastructure` を書かない限り、ドメイン層からインフラ層の型を使うことはコンパイラが許しません。詳しくは第7章-8の `Cargo workspaceに分割するタイミング` を参照してください。

## どれを選ぶべきか

結論から言えば、どの名前を採用するかは重要ではありません。重要なのは、次の点がチーム内で合意されていることです。

- どのディレクトリ(モジュール)に何を置くか
- 依存はどの方向に向かうか
- 外部の技術はどこでトレイトとして抽象化するか

チームで用語を統一するために、1つのアーキテクチャの名前を借りるのは有効です。ただし、名前に合わせてディレクトリを増やしすぎると、かえって構成が複雑になります。

本書のサンプルが3層に留めているのは、学習段階で「依存の方向」という本質に集中するためです。

## よくある誤解

- クリーンアーキテクチャの図にある層を、すべてディレクトリとして作る必要があると思いがち
- ヘキサゴナルアーキテクチャとDDDは、同じものだと考えがち
- アーキテクチャを決めれば、ドメインモデルの設計も自然に良くなると思いがち

これらのアーキテクチャは、ドメインモデルを技術から守るための「入れ物」です。入れ物を整えても、中に入るドメインモデルが貧弱なら、DDDの効果は得られません。ドメインモデルの設計(第4章)と、入れ物の設計(この章)は、別々に考える必要があります。

次章では、ドメインモデルを作り込む方式と、手続き的に処理を書く方式の使い分けを見ます。
