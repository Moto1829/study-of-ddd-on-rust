# 第7章-4 DB連携と永続化モデルの分離

DDDを実務へ持ち込むとき、多くの人が最初にぶつかるのがDB連携です。ここでは「ドメインモデルをそのままDBの形にしない」という基本方針を、Rustのコードでどう扱うかを整理します。

この章は、永続化モデルとドメインモデルの境界に集中する章です。トランザクションの切り方そのものは `トランザクション境界とApplication Service` で扱っているため、ここでは境界の置き場所だけを主題にします。

## なぜ分けるのか

DB上の表現とドメイン上の表現は、たいてい一致しません。

- DBでは文字列だが、ドメインではValue Objectにしたい
- DBではNULL許容だが、ドメインでは必須にしたい
- DBでは複数カラムだが、ドメインでは1つの概念として扱いたい

この差を無視すると、ドメインモデルが永続化都合に引っ張られやすくなります。

たとえば、DB都合で `status` を文字列カラムにしているからといって、ドメイン側まで `String` で持ち始めると、`open` と `Open` の揺れや未知の値の混入をあちこちで警戒しなければなりません。Value Objectやenumに閉じ込めたい厳密さが、永続化モデルの都合で崩れてしまいます。

## TaskRow を使った変換例

このタスク管理アプリでは、`TaskRow` という永続化モデルの例を追加しています。これはDBの行に近い形でデータを受けるための中間表現です。

```rust
pub struct TaskRow {
    pub id: String,
    pub title: String,
    pub status: String,
}
```

そして、`TaskRow` から `Task` への変換は `TryFrom` で表現しています。

```rust
impl TryFrom<TaskRow> for Task {
    type Error = TaskError;

    fn try_from(row: TaskRow) -> Result<Self, Self::Error> {
        let id = TaskId::new(row.id)?;
        let title = TaskTitle::new(row.title)?;
        let status = TaskStatus::from_str(&row.status)?;

        Ok(Task::restore(id, title, status))
    }
}
```

この形にしておくと、DBから不正値が来たときにも、ドメインモデルへ侵入する前に検知できます。

逆方向の変換も分けておくと、保存時にどの情報をDBへ落とすのかが明確になります。

```rust
impl From<&Task> for TaskRow {
    fn from(task: &Task) -> Self {
        Self {
            id: task.id().to_string(),
            title: task.title().as_str().to_owned(),
            status: task.status().as_str().to_owned(),
        }
    }
}
```

この往復を分ける利点は、DB表現を変えたときの影響範囲がInfrastructureに留まりやすいことです。たとえば `status` を文字列から整数コードへ変える場合でも、ドメインモデル全体を引きずらずに済みます。

## 変換でどこまで厳密に失敗させるか

DBから復元するときは、「多少おかしくても読めるようにする」より、「壊れたデータを早く見つける」方が保守しやすいことが多いです。

たとえば次のようなケースでは、暗黙に補正するより失敗として扱う方が安全です。

- 空文字の `id`
- 制約を超えた `title`
- 未知の `status`
- ドメイン上必須なのに NULL だった値

特に学習段階では、復元失敗を明示した方が「どこからどこまでがドメインの責務か」が見えやすくなります。壊れたデータを無理に吸収する設計は、後から不整合の原因を追いにくくします。

## NULL とオプショナル値をどう扱うか

DBでは NULL が使えても、ドメイン上それが「値が存在しない」を意味するのか、「まだ設定されていない暫定状態」を意味するのかは区別が必要です。

Rustでは `Option<T>` があるため、NULL をそのまま `Option` に対応付けたくなります。しかし本当に `Option` が自然かは、ドメインの意味で判断するべきです。

たとえば期限が未設定でよいなら `Option<TaskDeadline>` は自然です。一方で、必須のタイトルがNULLになり得るのは、DB都合のゆがみです。この場合は `Option<TaskTitle>` にして受け流すより、復元エラーにした方が筋が通ります。

## SQLやORMの型をどこまで露出させるか

実務では `sqlx::FromRow` や ORM のエンティティ型が便利に見えます。実際、Infrastructure層では積極的に使ってよいです。ただし、その型をそのままドメイン層まで運ばないことが重要です。

分離の基準は単純です。

- SQLやORMの都合を知ってよいのはInfrastructure層
- ドメイン層が知るのは業務上の型とルールだけ
- アプリケーション層はユースケースの入出力とトランザクション境界に集中する

この境界を守っておくと、ライブラリ変更の影響が局所化します。`sqlx` から `SeaORM` へ変えたくなったときに、痛みがInfrastructure内で済むのはこのためです。

## Rustで現実的に使う選択肢

Rustでは、次のような選択肢が現実的です。

- `sqlx`: SQLを自分で管理したいとき
- `SeaORM`: ORMベースで進めたいとき
- `tokio-postgres`: 低レベル寄りに制御したいとき

どのライブラリを使うにしても、重要なのはライブラリ依存をInfrastructure層へ閉じ込めることです。ドメイン層はテーブル定義や接続プールを知るべきではありません。

さらに言えば、選定基準もDDDそのものより実装都合で考えて構いません。

- SQLを明示的に管理したいなら `sqlx`
- ある程度CRUD中心で組みたいなら `SeaORM`
- 接続や実行制御を細かく握りたいなら `tokio-postgres`

重要なのはライブラリ名ではなく、どの選択肢でも「DBアクセスの詳細を境界の外へ漏らさない」ことです。

## 失敗しやすい設計

典型的なのは、永続化モデルとドメインモデルを最初から同一structで兼用してしまうことです。小規模なうちは楽に見えますが、次のような要求が入ると破綻しやすくなります。

- DBには監査用カラムが必要
- 画面からは受けない内部状態が増える
- enumの保存形式を変えたい
- 将来の移行期間だけ旧カラムと新カラムを併存させたい

こうした変更は実務では珍しくありません。同一structで抱え込むと、ドメインモデルがインフラ変更に引きずられます。

もう1つの失敗は、Repository実装の中で都度バラバラに変換することです。変換責務を `TryFrom<TaskRow>` や `From<&Task>` に寄せておくと、どこで整合性を確認しているかが追いやすくなります。

## まとめ

DB連携で大切なのは、DBを避けることではなく、DB都合の責務をドメイン層へ侵入させないことです。`TaskRow` のような中間表現を置くだけでも、境界はかなり明確になります。

実務で見るべきポイントを最後にまとめると、次の3つです。

1. DBの行をそのままドメインモデルにしない
2. 復元時の失敗を曖昧に吸収しない
3. SQLやORMの詳細をInfrastructure層に閉じ込める

この3つを守るだけでも、題材アプリケーションのような小さな構成から実務寄りの構成へ拡張しやすくなります。
