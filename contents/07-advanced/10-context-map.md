# 第7章-10 Context Mapで境界どうしの関係を整理する

第7章-9の `Bounded Contextをどう見つけるか` では、言葉の意味が変わる場所に境界を引く考え方を扱いました。しかし境界を引いただけでは終わりません。複数の Bounded Context は、互いにデータをやり取りしながら動きます。その関係を整理したものが Context Map です。

## なぜ関係を整理するのか

境界を切っても、境界どうしの関係が曖昧なままだと、次のような問題が起きます。

- 片方のチームの変更で、もう片方のシステムが突然壊れる
- 相手のモデルの言葉が、自分のモデルにいつの間にか入り込む
- どちらが仕様を決めるのかで、チーム間の調整が毎回もめる

Context Map は、こうした問題を「技術」ではなく「関係」の問題として捉えるための道具です。チーム間の力関係や協力の度合いが、そのまま設計に反映されるからです。

## 上流と下流

関係を整理する基本は、**上流(Upstream)** と **下流(Downstream)** です。

- 上流: モデルやデータを提供する側。変更が下流に影響する
- 下流: 上流のモデルやデータを利用する側。上流の変更の影響を受ける

たとえば、タスク管理アプリがユーザー情報を「アカウント管理」コンテキストから取得するなら、アカウント管理が上流、タスク管理が下流です。

```text
[アカウント管理] ──(U)──→(D)── [タスク管理]
   上流                          下流
```

上流と下流を決めることで、「どちらの言葉を正とするか」「変更のときに誰が誰に合わせるか」が明確になります。

## 関係のパターン

DDDでは、Context どうしの関係を次のようなパターンに分類しています。

### Partnership(パートナーシップ)

2つのチームが対等に協力し、両方のコンテキストを同時に変更していく関係です。片方だけでは成功できず、一緒にリリースします。

密に連携できる代わりに、調整コストが高くなります。同じ組織内で、目標を共有しているチームどうしに向いています。

### Shared Kernel(共有カーネル)

2つのコンテキストが、モデルの一部を共有する関係です。共有部分は両チームの合意なしに変更できません。

Rustでは、共有部分を独立したクレートやモジュールにすることで表現できます。

```text
src/
  shared_kernel/
    user_id.rs     # 両方のコンテキストで同じ意味を持つ
  personal_task/
  project_workflow/
```

便利ですが、共有部分が大きくなると、結局1つのモデルに戻ってしまいます。第7章-9で「`shared` を安易に増やしすぎない」と書いたのはこのためです。本当に意味が同じで、変更頻度の低いもの(ID型など)に限定するのが安全です。

### Customer/Supplier(顧客/供給者)

上流(供給者)が下流(顧客)の要望を聞きながら開発を進める関係です。下流は上流に要望を出せますが、最終的に何を提供するかは上流が決めます。

下流の要望が上流の計画に反映される仕組み(定期的な打ち合わせ、共同でのテスト作成など)があることが前提です。

### Conformist(順応者)

下流が、上流のモデルをそのまま受け入れる関係です。上流が下流の要望を聞く動機を持たない場合に生まれます。

たとえば、大手のSaaSのAPIを使うとき、自分たちの都合でAPIを変えてもらうことはできません。上流のモデルに合わせるしかありません。

順応することは必ずしも悪いことではありません。上流のモデルが十分に良く、自分たちのコアドメインに関係しないなら、翻訳のコストを払わずに済みます。

### Anti-Corruption Layer(腐敗防止層)

下流が、上流のモデルを自分たちのモデルに翻訳する層を設ける関係です。上流のモデルが自分たちの業務に合わない場合や、上流の変更から自分たちのモデルを守りたい場合に使います。

詳しくは次章の `腐敗防止層で外部モデルを翻訳する` で扱います。

### Open Host Service(公開ホストサービス)

上流が、多くの下流に向けて、整備されたAPIを公開する関係です。下流ごとに個別対応するのではなく、共通のプロトコルを用意します。

### Published Language(公表された言語)

コンテキスト間でやり取りするデータの形式を、ドキュメント化された共通の言語として定める関係です。JSON Schema、OpenAPI、Protocol Buffers などで定義されたデータ形式がこれにあたります。

Open Host Service と組み合わせて使われることが多く、上流は内部モデルではなく Published Language で外部と通信します。こうすると、上流は内部モデルを自由に変更できます。

### Separate Ways(別々の道)

2つのコンテキストを統合せず、独立して作る関係です。統合のコストが、得られる利益に見合わない場合に選びます。

たとえば、タスク管理と経費精算が同じ「担当者」の概念を持っていても、連携の必要がなければ、それぞれが独自に管理する方が単純です。

## パターンの選び方

パターンの選択は、技術よりも組織の状況で決まります。

| 状況 | 向いているパターン |
|---|---|
| 同じチーム、または密に連携できるチーム | Partnership、Shared Kernel |
| 上流が下流の要望を聞いてくれる | Customer/Supplier |
| 上流が外部の会社や、変更を頼めないシステム | Conformist、Anti-Corruption Layer |
| 上流のモデルが自分たちのコアドメインに合わない | Anti-Corruption Layer |
| 多数の下流がいる | Open Host Service + Published Language |
| 連携の価値が低い | Separate Ways |

特に重要な判断は、**コアドメインを守るかどうか**です。上流のモデルがコアドメインに入り込むと、自分たちの業務の言葉が上流の言葉に置き換わってしまいます。コアドメインに関わる連携では、Conformist ではなく Anti-Corruption Layer を選ぶ価値があります。

## Context Map を描く

Context Map は、複雑な記法を使う必要はありません。箱と矢印、そしてパターンの名前があれば十分です。

```text
                 [アカウント管理]
                  OHS / PL
                     │
                     │ U
                     ↓ D
[通知サービス] ←──── [タスク管理] ────→ [外部カレンダーAPI]
 Customer/Supplier   (コアドメイン)     ACL で翻訳
```

この図から、次のことが読み取れます。

- タスク管理はコアドメインであり、外部カレンダーAPIのモデルからは ACL で守っている
- アカウント管理は公開APIと共通データ形式でユーザー情報を提供している
- 通知サービスとは、要望を出し合える関係にある

## Rustのコードでの表れ方

Context Map のパターンは、コード上では次のように表れます。

| パターン | Rustでの典型的な表現 |
|---|---|
| Shared Kernel | 複数のモジュールから参照される共有モジュールやクレート |
| Conformist | 外部クレートの型を、そのままドメイン層で使う |
| Anti-Corruption Layer | 外部の型を自分の型へ変換する `From`/`TryFrom` 実装と、それをまとめた Adapter |
| Published Language | `serde` で直列化するDTOの型。OpenAPIなどから生成することもある |
| Separate Ways | モジュール間に `use` が存在しない |

モジュール間の `use` を眺めると、意図しない依存(Separate Ways のはずが参照している、ACL を通さずに外部の型を使っている、など)を見つけられます。

## よくある誤解

- Context Map は大規模システムのための図であり、小さなチームには関係ないと思いがち
- Shared Kernel を使えば、重複がなくなって効率が上がると考えがち
- Conformist は手抜きであり、常に避けるべきだと思いがち

小さなチームでも、外部APIやSaaSとの連携は必ずあります。その関係を「順応するのか、翻訳するのか」と意識するだけで、設計の判断がしやすくなります。
