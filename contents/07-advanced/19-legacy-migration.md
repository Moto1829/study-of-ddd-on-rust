# 第7章-19 既存システムにDDDを導入する

本書では、新しく作るタスク管理アプリを題材にDDDを学んできました。しかし実務では、ゼロから作れる機会は多くありません。すでに動いているシステムがあり、そこにDDDの考え方を持ち込みたい、という状況の方がはるかに一般的です。この章では、既存システムにDDDを少しずつ導入する方法を扱います。

## 全面的な書き直しは避ける

既存のコードが複雑で読みにくいと、すべてを書き直したくなります。しかし、全面的な書き直しは、次の理由で失敗しやすいことが知られています。

- 既存のコードには、文書化されていない業務ルールが大量に埋め込まれている
- 書き直しが終わるまで、新機能の追加や不具合の修正が止まる、または二重に必要になる
- 書き直しの完了時期を見積もるのが難しく、途中で頓挫しやすい

DDDの導入は、既存システムを動かし続けながら、少しずつ進めるのが現実的です。

## まず Context Map を描く

最初にやるべきことは、コードを書くことではなく、現状を理解することです。既存システムの中に、どんな業務領域があり、それらがどうつながっているかを Context Map として描きます。

既存システムの多くは、明確な境界のない、1つの大きなモデルになっています。これを**大きな泥団子(Big Ball of Mud)** と呼びます。

```text
┌─────────────────────────────────────┐
│          既存システム(泥団子)          │
│  タスク・ユーザー・課金・通知・レポート   │
│  が1つの DB と1つのモデルで混在している  │
└─────────────────────────────────────┘
```

泥団子の中にも、業務的なまとまりはあります。それを見つけて、第3章-4の方法で、どこがコアドメインかを判断します。DDDを導入する価値が最も高いのは、コアドメインです。

## バブルコンテキスト

既存システムの中に、DDDで設計した小さな領域を作る方法を、**バブルコンテキスト(Bubble Context)** と呼びます。泥団子の中に、きれいな泡を1つ作るイメージです。

```text
┌─────────────────────────────────────┐
│          既存システム(泥団子)          │
│                                     │
│     ┌───────────────────────┐       │
│     │ バブルコンテキスト       │       │
│     │ (新しいドメインモデル)   │←─ ACL │
│     └───────────────────────┘       │
│                                     │
└─────────────────────────────────────┘
```

バブルの中では、Value Object、Entity、Repository などを使ってドメインモデルを作ります。そして、バブルと既存システムの間に、第7章-11で扱った腐敗防止層(ACL)を置きます。

ACL がなければ、既存システムのモデルがバブルの中に入り込み、すぐに泥団子に戻ってしまいます。

### Rustでの例

既存システムが、タスクを次のような構造体で扱っているとします。

```rust
// 既存のコード(変更しない)
pub struct LegacyTask {
    pub id: i64,
    pub name: String,
    pub done: bool,
    pub deleted: bool,
    pub flag1: Option<String>, // 誰も意味を覚えていない
}
```

新しい機能をバブルコンテキストとして作り、ACL で既存の構造体と変換します。

```rust
// バブルコンテキストの ACL
impl TryFrom<&LegacyTask> for Task {
    type Error = TaskError;

    fn try_from(legacy: &LegacyTask) -> Result<Self, Self::Error> {
        let status = match (legacy.done, legacy.deleted) {
            (_, true) => TaskStatus::Archived,
            (true, false) => TaskStatus::Completed,
            (false, false) => TaskStatus::Open,
        };

        Ok(Task::restore(
            TaskId::new(legacy.id.to_string())?,
            TaskTitle::new(&legacy.name)?,
            status,
        ))
    }
}
```

`done` と `deleted` という2つの真偽値の組み合わせを、`TaskStatus` という1つの enum に翻訳しています。既存システムでは `done = true, deleted = true` のような曖昧な組み合わせがありえますが、バブルの中では3つの状態のどれかに確定します。

`TaskTitle::new` が失敗すれば、既存のデータにルールを満たさないもの(空のタスク名など)があることがわかります。これは、既存システムに隠れていたデータ品質の問題を発見するきっかけにもなります。

## ストラングラーパターン

バブルコンテキストを少しずつ広げ、最終的に既存システムを置き換えていく方法を、**ストラングラー(Strangler Fig)パターン**と呼びます。絞め殺しのイチジクという植物が、宿主の木に巻きついて成長し、最終的に宿主に取って代わる様子に由来しています。

進め方は次の通りです。

1. **入口を1つにする**: 既存システムへのリクエストを、振り分けを行う層(ルーターやプロキシ)経由にする
2. **1つの機能を新しく作る**: たとえば「タスクの完了」だけを、DDDで設計した新しいコードで実装する
3. **振り分けを切り替える**: 「タスクの完了」のリクエストだけを新しいコードへ送る
4. **既存のコードを削除する**: 新しいコードが安定したら、既存の「タスクの完了」の処理を削除する
5. **繰り返す**: 次の機能について、2から4を繰り返す

```text
        [振り分け層]
        ↙         ↘
 [新しいコード]   [既存システム]
  タスクの完了    その他すべて
     ↓               ↓
     └──── 共有のDB ───┘
```

既存システムを動かしたまま、1機能ずつ移行できます。どの時点でも中断でき、それまでの成果は残ります。

## DBを共有する期間の注意

ストラングラーパターンの途中では、新しいコードと既存システムが同じDBを使うことが多くなります。このとき、新しいドメインモデルのルールを、既存システムが知らずに破る可能性があります。

たとえば、新しいコードでは「アーカイブ済みのタスクは名前を変更できない」というルールを守っていても、既存システムがDBを直接更新すれば、ルールは破られます。

対策としては、次のようなものがあります。

- **移行の順番を工夫する**: あるデータを更新する機能は、まとめて新しいコードへ移す
- **DBの制約を使う**: 守りたいルールの一部を、DBのチェック制約やトリガーでも守る
- **変換を厳密にする**: 前述の `TryFrom` のように、DBから読み込む時点でルール違反を検出する

## 小さく始める

DDDの導入は、大きな計画から始める必要はありません。既存のコードの中でも、次のような小さな改善から始められます。

### Value Object を1つ導入する

もっとも効果が高く、リスクが低い最初の一歩です。既存のコードで `String` として扱われている値のうち、妥当性検証が散らばっているものを1つ選び、Value Object にします。

```rust
// 変更前: あちこちで同じ検証をしている
if email.is_empty() || !email.contains('@') { /* ... */ }

// 変更後: 検証は1箇所に
let email = EmailAddress::new(input)?;
```

関数の引数の型を `String` から `EmailAddress` に変えると、呼び出し元がすべてコンパイルエラーになり、検証していない経路が見つかります。

### 状態を enum にする

文字列や数値、複数の真偽値で表されている状態を、enum に置き換えます。前述の `done` と `deleted` の例のように、ありえない組み合わせが排除されます。

### ルールを1つ Entity に移す

複数の場所に重複している業務ルールを1つ選び、Entity のメソッドに移します。第7章-18で扱った移行の手順が使えます。

## 導入を進めるための工夫

### テストで既存の振る舞いを固定する

既存のコードを変更する前に、現在の振る舞いを確認するテストを書いておきます。業務ルールが文書化されていないシステムでは、このテストが「現状の仕様」になります。仕様として正しいかどうかわからない振る舞いも、まずはそのまま固定し、変えるときは業務担当者に確認します。

### ユビキタス言語の用語集を作る

既存システムでは、同じ概念に複数の名前がついていることがよくあります(`task`、`todo`、`item`、`job` など)。業務担当者と話しながら、正しい名前を決めて用語集を作ります。新しく書くコードでは、この用語集の名前を使います。

### 成果を見えるようにする

DDDの導入は、短期的には目に見える成果が出にくい活動です。「この Value Object を導入してから、この種類の不具合がなくなった」「この機能の変更にかかる時間が短くなった」といった具体的な成果を記録し、チームや関係者に共有すると、継続しやすくなります。

## よくある誤解

- DDDを導入するには、システムを全面的に書き直す必要があると思いがち
- 既存システムのモデルを少しずつ修正していけば、いずれきれいになると考えがち
- DDDの導入は、技術的な判断だけで進められると思いがち

ACL なしで既存のモデルを修正しようとすると、既存のコードとの互換性に縛られ、結局は泥団子の一部になってしまいます。新しいモデルは、ACL で守られたバブルの中で育てるのが確実です。また、どこから導入するかは、コアドメインの判断という事業上の判断に基づくため、業務担当者との協力が欠かせません。
