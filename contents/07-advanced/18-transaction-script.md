# 第7章-18 トランザクションスクリプトとドメインモデルの使い分け

DDDを学ぶと、すべての処理をドメインモデルで表現したくなります。しかし、ビジネスロジックを組み立てる方法は、ドメインモデルだけではありません。この章では、もう1つの代表的な方法であるトランザクションスクリプトと比較し、どちらをいつ選ぶべきかを整理します。

## トランザクションスクリプトとは

トランザクションスクリプトは、1つのユースケースを1つの手続き(関数)として書く方法です。データの取得、ルールの確認、更新を、上から順番に書いていきます。

タスクの完了をトランザクションスクリプトで書くと、次のようになります。

```rust
pub fn complete_task(db: &mut Db, task_id: &str) -> Result<(), AppError> {
    let row = db
        .find_task(task_id)?
        .ok_or(AppError::NotFound)?;

    if row.status == "completed" {
        return Err(AppError::AlreadyCompleted);
    }
    if row.status == "archived" {
        return Err(AppError::NotOpen);
    }

    db.update_task_status(task_id, "completed")?;
    Ok(())
}
```

同じ処理をドメインモデルで書くと、本書のサンプルの形になります。

```rust
pub fn complete_task(&mut self, task_id: impl Into<String>) -> Result<TaskOutput, TaskApplicationError> {
    let task_id = TaskId::new(task_id)?;
    let mut task = self.repository.find_by_id(&task_id).ok_or(/* ... */)?;

    task.complete()?; // ルールは Task が持つ

    self.repository.save(task);
    // ...
}
```

違いは、**ルールがどこにあるか**です。トランザクションスクリプトでは、ルールが手続きの中に書かれます。ドメインモデルでは、ルールが `Task` の中に閉じ込められます。

## トランザクションスクリプトの利点

トランザクションスクリプトは、悪い方法ではありません。

- **わかりやすい**: 処理が上から下へ読めるため、初めて読む人にも理解しやすい
- **速く書ける**: Value Object や Repository などの準備が不要
- **ルールが単純なら十分**: 入力を受け取って保存するだけなら、ドメインモデルは過剰になる

## トランザクションスクリプトの問題

問題は、ルールが増えてきたときに表れます。

タスクの名前変更、完了、アーカイブ、期限の変更など、ユースケースが増えると、「Open 状態でないタスクは変更できない」というルールが、それぞれの関数に重複して書かれていきます。

```rust
pub fn rename_task(/* ... */) {
    if row.status != "open" { return Err(/* ... */); }
    // ...
}

pub fn change_deadline(/* ... */) {
    if row.status != "open" { return Err(/* ... */); }
    // ...
}

pub fn assign_task(/* ... */) {
    // ここにチェックを書き忘れた
    // ...
}
```

ルールが変わったとき、すべての関数を正しく直せる保証はありません。書き忘れた関数があっても、コンパイラは教えてくれません。

ドメインモデルなら、ルールは `Task` の中の1箇所にまとまっています。また、`Task` のフィールドが非公開なので、ルールを経由せずに状態を変えることができません。

## 貧血ドメインモデル

トランザクションスクリプトとドメインモデルの中間に、**貧血ドメインモデル(Anemic Domain Model)** と呼ばれる状態があります。見た目はドメインモデルですが、中身はトランザクションスクリプトです。

```rust
// データだけを持つ「Entity」
pub struct Task {
    pub id: String,
    pub title: String,
    pub status: TaskStatus,
}

// ルールはすべてサービスに書かれている
impl TaskService {
    pub fn complete_task(&mut self, task_id: &str) -> Result<(), AppError> {
        let mut task = self.repository.find(task_id)?;
        if task.status != TaskStatus::Open {
            return Err(AppError::NotOpen);
        }
        task.status = TaskStatus::Completed;
        self.repository.save(task)?;
        Ok(())
    }
}
```

`Task` という型や `Repository` という名前はあっても、ルールは `TaskService` に散らばっています。フィールドが `pub` なので、誰でも `task.status` を書き換えられます。

貧血ドメインモデルは、ドメインモデルの手間(型や層の分離)と、トランザクションスクリプトの問題(ルールの散乱)の両方を抱えた、最も避けるべき状態です。

## 貧血を見分けるチェックリスト

次の項目に多く当てはまるなら、貧血ドメインモデルになっている可能性があります。

- Entity のフィールドがすべて `pub` になっている
- Entity のメソッドが、ゲッターとセッターだけである
- `XxxService` という名前の型に、ほとんどのロジックが集まっている
- ドメインのルールを確認するテストが、Service のテストにしかない
- Entity を見ても、どんな操作が許されているのかわからない

本書の `Task` は、フィールドが非公開で、`rename`、`complete`、`archive` という業務上の操作をメソッドとして持っています。これがドメインモデルの基本形です。

## 使い分けの基準

どちらを選ぶかは、ドメインの複雑さで決まります。

| 状況 | 向いている方式 |
|---|---|
| ルールが少なく、ほぼ CRUD である | トランザクションスクリプト |
| 状態遷移があり、状態によって許される操作が変わる | ドメインモデル |
| 同じルールが複数のユースケースで使われる | ドメインモデル |
| 支援サブドメインや汎用サブドメイン | トランザクションスクリプトで十分なことが多い |
| コアドメイン | ドメインモデル |
| 一時的なスクリプトや、データの移行処理 | トランザクションスクリプト |

第3章-4の `コアドメインとサブドメインを見分ける` で扱ったように、DDDはすべての領域にドメインモデルを適用することを求めていません。同じアプリケーションの中で、コアドメインはドメインモデルで、支援サブドメインはトランザクションスクリプトで、という使い分けは自然なことです。

## トランザクションスクリプトからドメインモデルへ

最初はトランザクションスクリプトで始め、ルールが増えてきたらドメインモデルへ移行する、という進め方も現実的です。移行は、次の順番で少しずつ進められます。

1. **Value Object を導入する**: `String` のタイトルを `TaskTitle` に置き換え、妥当性検証を1箇所にまとめる
2. **状態を enum にする**: `"completed"` のような文字列を `TaskStatus` に置き換える
3. **重複したルールを Entity のメソッドに移す**: 複数の関数にある `if status != "open"` を `Task` のメソッドにまとめる
4. **フィールドを非公開にする**: Entity のメソッド以外から状態を変えられないようにする

Rustでは、4のステップでフィールドを非公開にすると、直接書き換えている箇所がすべてコンパイルエラーになります。コンパイラが、移行の残りの作業を教えてくれます。

## よくある誤解

- トランザクションスクリプトは、DDDに反する悪い書き方だと思いがち
- `Entity` や `Repository` という名前を使っていれば、ドメインモデルになっていると考えがち
- ドメインモデルにすれば、必ずコードが良くなると思いがち

トランザクションスクリプトは、単純な問題には最適な解決策です。避けるべきなのは、複雑なルールをトランザクションスクリプトで書き続けることと、ドメインモデルのつもりで貧血ドメインモデルを作ることです。
